# Методика Repo Health Score

Расчёт детерминированный: одни и те же метрики дают один и тот же балл. Модель языка в формуле не участвует. Арифметика живёт в `health/scoring.py`, сбор фактов — в `health/*_scan.py`, итог по репозиторию — в `health/orchestrator.py`.

Кнопка «Сводка YandexGPT» на карточке просит YandexGPT Lite пересказать уже записанные балл и находки. Текст лежит в `Scan.raw["ai"]` и попадает в Markdown. Нет ключа или ошибка модели — карточка остаётся без сводки, балл не меняется.

## Итог

Балл категории — целое от 0 до 100 или пустое значение «Нет данных».

Итог считается только по категориям, где балл есть:

```text
эффективный вес = базовый вес × полнота данных категории
Repo Health Score = round(сумма(балл × эффективный вес) / сумма эффективных весов)
```

Полнота данных — доля веса подметрик, которые удалось измерить. Категория, собранная наполовину, тянет итог слабее полностью измеренной. Если измерить не удалось ни одну категорию, итог тоже «Нет данных», а не ноль.

Базовые веса совпадают с ориентиром ТЗ. Сумма равна 1.

| Категория | Вес | Когда считается |
|---|---|---|
| Безопасность | 20% | Личный анализ с PAT |
| Состояние кода | 20% | Всегда, если есть дерево файлов |
| Активность | 15% | Всегда |
| Документация | 15% | Всегда, если есть дерево файлов |
| CI/CD | 15% | Личный анализ с PAT |
| Issues | 15% | На каждом скане. Пустой список или ошибка чтения — «Нет данных» |

В плановом публичном скане Security и CI/CD не собираются. Их базовые 35% не обнуляют Score: вес переходит к документации, активности, issues и состоянию кода. Личный скан того же публичного репозитория считает все шесть категорий, и этот итог стоит в рейтинге, пока его не сменит следующий успешный плановый скан. На публичной странице строки этих двух категорий скрыты. Они видны на карточке из «Моих репозиториев» и у непубличного репозитория.

Пустой репозиторий (`is_empty` или нет ветки по умолчанию) — отдельный случай. Категории и итог помечаются «Нет данных»: скан прошёл, но измерить нечего. Ноль сюда не пишется.

Лайки, сердца и бриллианты SourceCraft в формулу не входят. Ноль лайков не снижает балл, рост реакций его не поднимает.

## Нет данных и плохой балл

«Нет данных» — это `total = null`. Ноль — измеренный плохой результат.

| Ситуация | Что записывается |
|---|---|
| Публичный запуск, CI/CD и Security | Нет данных: эти API для чужого репозитория не вызываются |
| Нет PAT у владельца скана, CI или Security | Нет данных |
| AppSec не запускался, ещё идёт, упал или ответил 401/403/404 | Нет данных. Чистый завершённый скан с нулём находок — высокий балл, не пустота |
| Дерево файлов или список issues/MR недоступен | Нет данных по затронутой метрике |
| Список issues пуст или его не удалось прочитать | Категория Issues — «Нет данных». Число issues в каталоге само по себе скан не отменяет |
| Нет README | Низкий балл документации, не «Нет данных» |
| Нет `.sourcecraft/ci.yaml` при личном анализе | Балл CI низкий, категория доступна |
| Репозиторий из одних данных без исходников | Низкий балл структуры в состоянии кода, итог при этом не принудительно 0 |
| Ошибка 429 или 5xx | Задача ретраится, отсутствие ответа не подменяется нулём |

На карточке и в Markdown категории без балла подписаны «Нет данных» и указана причина. Строка под списком говорит, что их вес перераспределён.

Флаг `is_preliminary` пишется в сырые данные скана, если сумма базовых весов категорий с баллом больше нуля и меньше 0.5. На карточке и в рейтинге вместо числа показывают, что оценки недостаточно из‑за доступности данных API SourceCraft и связанных сервисов (не сбой Repo Health). В кэш `Repository.health_score` такой итог не пишется.

`Repository.health_score` обновляется только из `SUCCESS` без preliminary. `PARTIAL` кэш не меняет. Если последний скан `FAILED`, на карточке показывают предыдущий `SUCCESS` и явно пишут, что свежий анализ с ошибкой.

## Как складывается балл категории

У каждой категории есть подметрики со своими весами (сумма 1). Недоступная подметрика выпадает из среднего, её вес не штрафует балл, но снижает полноту данных.

Линейная шкала `scale(значение, худшее, лучшее)` зажимает результат в 0..100. Если «худшее» больше «лучшего», меньшее значение лучше: так устроены часы до ответа и длительность пайплайна.

### Документация, 15%

Смотрит дерево файлов и текст README.

| Подметрика | Вес | Балл |
|---|---|---|
| Качество README | 30% | Нет файла — 0. Иначе половина за длину (500 символов — 0, 3000 и больше — 100) и половина за раздел со структурой проекта |
| Лицензия | 20% | Нет файла — 0. Файл есть, тип не распознан — 50. Тип распознан — 100 |
| Локальный запуск | 10% | 100, если в README есть инструкция запуска, иначе 0 |
| Сборка и тесты | 10% | 100, если в README есть инструкция сборки или тестов, иначе 0 |
| CONTRIBUTING и CODEOWNERS | 15% | Доля найденных файлов из этих двух |
| Дополнительная структура | 15% | Доля из changelog, каталога `docs/`, шаблонов issue и шаблона MR |

Если README есть, но текст прочитать не удалось, качество README в среднее не входит.

### Активность, 15%

Плановый скан не клонирует репозиторий, поэтому коммиты в нём не участвуют.

| Подметрика | Вес без коммитов | Вес с коммитами |
|---|---|---|
| Давность последней активности | 40% | 35% |
| Коммиты за 30 дней | — | 20% |
| Merge request за 30 дней | 30% | 25% |
| Релизы за 30 дней | 30% | 20% |

Давность: до 7 дней — 100; от 7 до 30 — линейно до 60; от 30 до 90 — линейно до 0; старше 90 дней — 0. Дата берётся как максимум из `last_updated`, MR, релизов и, в личном скане, коммитов.

Счётчики за 30 дней: 0 — это 0 баллов. MR: 10 и больше — 100. Релизы: 3 и больше — 100. Коммиты считаются только в личном скане: 1 коммит — 15, 20 и больше — 100.

Контрибьюторы клиент API умеет запрашивать, в балл они не входят.

### Issues, 15%

Список issues запрашивается на каждом скане. Ноль открытых при непустом списке — это хороший сигнал по доле зависших, а не пустая категория. Пустая категория — когда список пуст или его не удалось прочитать.

Окно — 30 дней. Зависшая задача — открытая и без обновления больше 30 дней. Время до первого ответа считается по последним 30 задачам, где есть и дата создания, и первый комментарий.

| Подметрика | Вес | 0 баллов | 100 баллов |
|---|---|---|---|
| Доля зависших среди открытых | 35% | 50% и больше | 0% |
| Медиана до первого ответа | 30% | 168 часов и больше | 24 часа и меньше |
| Медиана до закрытия | 20% | 90 дней и больше | 7 дней и меньше |
| Доля закрытых среди созданных за 30 дней | 15% | 0% | 100% |

### Состояние кода, 20%

По дереву файлов. TODO/FIXME ищутся не больше чем в 30 текстовых файлах. Давность этих комментариев по git считается только в личном скане, потому что для неё нужен клон.

| Подметрика | Вес с давностью TODO | Вес без давности |
|---|---|---|
| Есть тесты | 25% | 30% |
| Нет закоммиченного мусора | 20% | 25% |
| Структура | 15% | 17% |
| Есть конфиг линтера | 15% | 17% |
| Манифест и lockfile | 10% | 11% |
| TODO/FIXME | 15% | 5% |

Тесты и линтер — 100 или 0 по наличию. Мусор: вендоренные зависимости, сгенерированные артефакты, бинарные файлы; каждый найденный класс вычитает равную долю из 100.

Структура: репозиторий без исходников и с табличными файлами — 0; плоская свалка файлов — 20; иначе 100. Для репозитория без исходников манифест зависимостей не штрафуется. Если исходники есть: манифест и lockfile — 100, только манифест — 70, ни того ни другого — 30.

TODO: 0 штук — 100, 40 и больше — 0. В личном скане доля комментариев старше 180 дней добавляет штраф до 30 баллов подметрики, полный штраф — при 50% и больше старых.

### CI/CD, 15%

Только личный анализ и только PAT SourceCraft, не токен Я ID. Ищется `.sourcecraft/ci.yaml` и список прогонов.

| Подметрика | Вес | Балл |
|---|---|---|
| Конфиг CI | 30% | Есть — 100, нет — 0 |
| Доля успешных завершённых прогонов | 55% | 0% — 0, 100% — 100 |
| Медианная длительность | 15% | 60 минут — 0, 5 минут и меньше — 100 |

Успех — статус `success`. Неуспех — `failed` и `timeout`. Нет конфига — категория доступна и балл низкий, потому что в формуле остаётся только нулевой признак конфига. Нет списка прогонов при живом конфиге — в среднее входят только доступные подметрики.

### Безопасность, 20%

Только личный анализ, только PAT, только платформенный AppSec: `GET /v1/scans/latest` и группы дефектов. Свой сканер уязвимостей сервис не запускает.

Балл считается по скану со статусом FINISHED. Открытые группы SCA, SAST и secrets со статусом не из закрытых (`resolved`, `solved`, `closed`, `false_positive`) дают штраф. Закрытые группы балл не снижают.

| Подметрика | Вес | Один открытый дефект обнуляет подметрику при штрафе |
|---|---|---|
| Прямой critical | 50% | 30 |
| Транзитивный critical | 35% | 20 |
| High, любой анализатор | 15% | 10 |

Штрафы одной критичности суммируются и зажимаются шкалой. Один прямой critical обнуляет свою подметрику (половину категории) и не трогает две другие: при чистых остальных балл категории около 50. Ноль открытых групп после FINISHED — 100.

## Рекомендации

Каждый сканер после балла пишет `Finding`: проблема, почему она важна, факты, действие, приоритет и оценка влияния.

Приоритет — четыре уровня: низкий, средний, высокий, критический. Если балл категории ниже 40, приоритет каждой её находки поднимается на одну ступень. Пустая категория приоритет не поднимает.

Сначала сканер считает, сколько баллов вернёт исправление внутри категории. Доля подметрики берётся среди тех, что реально посчитаны, и умножается на недобор этой подметрики до 100.

После агрегации это целые пункты общего Score. Вместе с текущим баллом они дают 100: недобор каждой посчитанной подметрики сидит в рекомендации, а округление раскладывается так, чтобы сумма не теряла пункт. Если несколько находок делят одну подметрику, обещание делится между ними и не превышает запас категории. На карточке это подпись «+N к Score», в Markdown — «ожидаемый прирост Repo Health Score».

На карточке список идёт по приросту к Score, затем по приоритету. В Markdown сначала по приоритету, затем по приросту. В отчёте у рекомендации есть действие и ссылка, если факт — это URL.

Примеры того, что порождает находку:

- нет README, лицензии, инструкции запуска, CONTRIBUTING;
- последняя активность старше 90 дней, нет MR или релизов за 30 дней;
- высокая доля зависших issues, долгий первый ответ или закрытие;
- нет тестов, линтера, lockfile, много TODO, data-only дерево, мусор в git;
- нет `.sourcecraft/ci.yaml`, доля успеха ниже 80%, медиана прогона дольше 30 минут;
- открытая группа critical или high в AppSec, со ссылкой на группу.

## Контрольные сценарии

Ожидание ниже — про направление балла, не про эталонное число.

| Сценарий | Ожидание |
|---|---|
| Нет README, дерево доступно | Документация низкая в публичном и личном скане |
| Дерево недоступно | Документация «Нет данных», не 0 |
| Публичный скан | CI и Security «Нет данных», итог по остальным категориям |
| Свой репозиторий без `.sourcecraft/ci.yaml` | CI низкий и доступен |
| Свой репозиторий, AppSec FINISHED и 0 групп | Security высокий |
| AppSec не запускался или 403 | Security «Нет данных» |
| Транзитивный critical в SCA | Security ниже, чем у чистого скана |
| Свежие коммиты и MR против тишины дольше 90 дней | Активность у свежего выше |
| 0 и 200 лайков при тех же остальных метриках | Итог не меняется |
| Одинаковые сырые метрики дважды | Одинаковые баллы |
